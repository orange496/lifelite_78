# 设计决策记录

这里记录的是**做过的取舍和理由**，不是使用说明。使用说明看 [`README.md`](../README.md)，数据结构看 [`data-schema.md`](data-schema.md)。

每条决策都写成「背景 → 决定 → 代价」，方便以后有人（包括未来的我们）推翻它之前先知道当初为什么这么做。

---

## 1. 用经典 `<script>` + 全局命名空间，不用 ES Module

**背景**：交付要求是「双击 `index.html` 就能用」。浏览器对 `file://` 下的 `type="module"` 会按 CORS 规则拦截，脚本直接不执行。

**决定**：六个脚本用经典 `<script>` 按顺序加载，各自用 IIFE 包起来，只往全局挂一个 `LL` 命名空间（`LL.CONST` / `LL.Util` / `LL.Storage` / `LL.Profile` / `LL.Goals` / `LL.Tasks` / `LL.Stats` / `LL.ui` / `LL.App`）。

**代价**：没有模块作用域，靠「文件顶部 `'use strict'` + IIFE」约束；脚本顺序必须写在 `index.html` 里且不能乱（storage → profile → goals → tasks → stats → app）。换来的是零构建、零依赖、双击即用，并且部署到 GitHub Pages 时不需要任何打包步骤。

## 2. 所有写操作只走 `LL.Storage.write()`

**背景**：五个键分散在四个模块里读写，很容易出现「改了目标但忘了更新 meta」，或者同一份数据两种写法。

**决定**：`storage.js` 是唯一写入口，`write()` 内部完成序列化、写入、更新 `meta.lastModified`。业务模块只调 `writeGoals` / `writeTasks` / `writeCheckins` / `writeProfile`。

**代价**：每次写都完整序列化整个数组，几千条数据时会变慢；以本项目的规模（个人一学期的目标）可以接受。收益是数据一致性有唯一保证点，出问题只看一个文件。

## 3. 等级由经验推导，不单独存真值

**决定**：`profile.level` 在读取时用 `levelFromExp(exp)` 重新计算，写入时只是把计算结果存进去方便展示。

**理由**：等级和经验是同一事实的两种表示，分开存就会不一致（尤其是导入旧备份之后）。推导出来永远不会错。

## 4. 只加不减：撤销完成、删除任务都不回收经验

**背景**：直觉上「撤销完成就该扣回经验」，但这会让「等级只增不降」变得不可能，也会诱导用户不敢点错。

**决定**：经验一旦发放就不再回收。撤销完成只清空 `completedAt`，删除任务、删除目标都不扣经验。完成目标重新打开时给出提示「已获得的经验不会收回」。

**代价**：用户可以通过「建任务 → 完成 → 删除」刷经验。这是刻意的取舍：这个应用的目标是**鼓励行动**，不是反作弊。刷经验的人至少真的建了任务、点了完成。

## 5. 幂等以 `completedAt` 为判据，经验按 `(source, refId)` 去重

**决定**：任务的完成状态只看 `completedAt` 是否为空；同时 `Profile.addExp` 对同一 `(source, refId)` 只发一次。

**理由**：双击、连点、两个标签页同时操作都会造成重复触发。单靠 UI 禁用按钮不可靠，所以在数据层兜底。`refId` 用任务 id / 目标 id / 日期 / 里程碑编号，天然唯一且不依赖自增。

## 6. 级联删除先删任务再删目标

**决定**：删除目标时先过滤并写入 `tasks`，再写入 `goals`。

**理由**：写入可能失败（比如存储满了）。先删任务的话，最坏情况是「目标还在、任务没了」，用户能看到一个空目标；反过来先删目标，任务会变成指向不存在目标的孤儿数据，列表里多出一批查不到归属的脏任务。两害相权，前者可恢复性更好。

删除前用确认框写明「该目标下的 N 个任务也会一起删除」，数字实时统计。

## 7. 已归档目标不能直接删除，要「彻底删除」

**决定**：归档是「收起来」，不是「待删除」。对已归档目标提供「彻底删除」，未归档目标必须先进归档才能彻底删除。

**理由**：归档误触的代价应该只是「多一个收起的卡片」，而不是数据消失。把「危险操作」放在离日常操作更远的地方，符合渐进式披露。

## 8. 统计与进度一律实时计算，不缓存

**决定**：进度、本周完成数、完成率、连续天数都在渲染时从数据层重算；不存中间状态，不做 memo。

**理由**：缓存失效是这类小应用最常见的 bug 来源（改完任务进度不变）。数据量小，重算的成本远低于维护缓存的成本。

## 9. 不引入图表库，趋势用纯 CSS 条形

**决定**：最近七天趋势用 7 个 `div` 的高度模拟条形，热力图用 CSS Grid 排 8×7 个格子。

**理由**：为了「零依赖 + 页面体积 < 200 KB」。图表库动辄几十上百 KB，而这里只需要七个柱子。

## 10. Service Worker 只在 http(s) 下注册

**决定**：`app.js` 里检查 `location.protocol !== 'file:'` 才注册 `sw.js`，失败只 `console.warn`，不影响应用使用。

**理由**：`file://` 下浏览器出于安全根本不支持 SW，硬注册会抛错并打断初始化流程。双击打开时「离线」本来就不需要 SW——文件在本地。部署到 GitHub Pages 后才有真正的离线缓存。

## 11. 删除任务用「10 秒撤销 Toast」，而不是确认框 + 回收站

**决定**：删除任务仍然先确认，但确认后给一个 10 秒的「撤销」按钮（`LL.ui.toast` 支持 `action`）。

**理由**：比回收站轻，比「确认了就没了」安全。10 秒是经验和可点击性的平衡：短到不打扰，长到够反应过来点错。

## 12. 单目标任务超过 20 条时默认折叠已完成区

**决定**：阈值是 `CONST.COLLAPSE_THRESHOLD = 20`，用户可手动展开/收起，选择按目标记住（只在本次会话内）。

**理由**：已完成列表会无限增长，长期使用后会把待办挤到屏幕外。20 条以内折叠反而碍事，所以只在真正变长时才折叠。

## 13. 导入整体校验、整体拒绝；覆盖前写备用键

**决定**：任何一条数据不合格就整份拒绝，不做「能导入多少导多少」；确认导入后先把旧数据写进 `lifelite.backup`，再逐键覆盖。

**理由**：部分导入会制造「一半新一半旧」的数据，比失败更难查。备用键让「手滑选错文件」有一个后悔药。

## 14. 读取到损坏的 JSON 时留档而不是静默清空

**决定**：解析失败时，把原始文本写进 `lifelite.corrupt`，然后用默认值继续运行，并通过 `takeNotice()` 告诉用户「有数据读取失败，已重置」。

**理由**：静默清空等于数据丢失且无从排查；留档至少还能手工抢救一次。

## 15. 不做深色模式

**背景**：方案里明确写了「深色模式为可选项，不进入验收标准」。

**决定**：这个版本不做。避免为了一个可选功能引入两套配色变量和 `prefers-color-scheme` 分支，把精力放在核心链路上。

**代价**：夜间使用时页面偏亮。后续要做的话，当前所有颜色都已经收敛在 `:root` 的设计令牌里，加一组覆盖变量即可，不需要改结构。

## 16. 已知问题写进文档而不是假装不存在

**决定**：把「修改系统时间/跨时区导致日期跳变」「localStorage 只在当前浏览器、换设备需手动导入导出」「刷经验漏洞」都写进 README 和本文件。

**理由**：一个作业项目最容易被问住的地方是「边界情况你怎么处理的」。诚实列出已知问题，比声称「全部处理」更可信。

## 17. 图标用脚本生成并提交 PNG

**决定**：`tools/make-icons.py` 是开发期一次性脚本，生成的三张 PNG 直接提交进仓库，运行时不需要 Python。

**理由**：图标要可复现（改配色时重跑一次），但交付物不能依赖构建环境。脚本是「可选的开发工具」，不是构建步骤。
